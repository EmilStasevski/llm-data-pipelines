# ADR 0010: Rust Track A contestants (a15/a16/a17) and the streaming reference / XL scale

- Status: accepted (Phase 4, 2026-11-07).
- Context: PLAN §8 defines a15 (Rust polars lazy), a16 (arrow-rs csv + rayon + regex + aho-corasick), a17 (pure Rust, max effort). The fast contestants run < 5 s at L, which gives low-confidence energy numbers (PLAN §14), so XL (10M rows) was needed; the in-memory reference would need ≈ 30 GB there.
- Decisions:
  - **Shared crate `zj-track-a`**: lexicon, text rules (§1 norm, §6 expand/fold/safety, §7 component via aho-corasick overlapping search, `doc_text`), output schema/builder, parallel Parquet row-group encoding (`ArrowRowGroupWriterFactory`). Two field-parser flavours with identical results: `fields::Regex` (spec regexes, a16) and `fields::Hand` (byte-level, a17). Both pass all 208 golden cases (`cargo test`).
  - **a17**: mmap + quote-aware chunk boundaries (parallel quote-parity counts, then memchr2 to the next unquoted LF, so quoted line breaks are never split), hand-written strict cp1252 decoder (table checked against encoding_rs; the five undefined bytes are errors like Python's codec), per-chunk transform + Parquet encoding in rayon, ordered append.
  - **a16**: encoding_rs → arrow-csv (UTF-8 only) → waves of 16k-row batches transformed with rayon → ArrowWriter. Empty CSV fields arrive as null and are mapped to "" (spec).
  - **a15**: 1:1 port of the Python Polars expressions (a10), cp1252 decoded in memory with encoding_rs, collected with `Engine::Streaming`: Python Polars 2.x `collect()` (default `engine="auto"`) runs the streaming engine, whereas `Auto` in the Rust crate 0.55 means in-memory. Unmeasured at L: in-memory 13.3 s → streaming 4.55 s. (This also explains why a10 lazy and a11 streaming measured alike.)
  - **Build setup shared by all Rust contestants** (what the Python wheels ship, so the comparison is about code, not toolchain defaults): `-C target-cpu=x86-64-v3` (`contestants/rust/.cargo/config.toml`) and jemalloc as global allocator (`tikv-jemallocator`; the Polars runtime links it, `_rjem_` symbols). Both had no visible effect on a16/a17 and did not explain the a15 gap (the engine choice did).
  - **Sortedness**: the input is in id order; every Rust contestant verifies strict order and otherwise sorts (a17: full re-materialise + sort; a16: re-read + sort + rewrite). Tested with a shuffled input.
  - **Streaming reference**: `zj_reference.track_a.run` writes 50k-row chunks and fails loudly on non-increasing ids. XL reference: 7 min, 268 MB peak RSS; XL is prefix-identical to L (first 1M rows, 0 differences).
  - **XL set** = contestants whose L median is < 10 s: a10, a11, a13, a15, a16, a17. a07 (cudf.pandas) at XL exhausted host RAM (stopped by the feasibility memory guard); a08 (map_elements) is limited to S/M like a02 (L took 203 s unmeasured, superlinear vs 3.7 s at M). Feasibility (unmeasured, 2026-11-07): Polars/DuckDB 28–33 s at 12–21 GB RSS; pandas a05/a06 ≈ 6 min at ≈ 24 GB and a09 109 s, so they stay at S/M/L, where their runs are already long.
- Verification: `zj_eval.verify_track_a` now compares all columns in one join with all DuckDB threads (XL: 48 s → 4.5 s; every query is deterministic via ORDER BY unique keys).
- Consequences: Rust builds use `--locked` and the release profile (fat LTO, 1 codegen unit, panic=abort). Clippy pedantic is clean with `-D warnings`.
